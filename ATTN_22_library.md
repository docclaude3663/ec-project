## 22.0. Концепт и границы

**Library это режим игрока**, мастерская и коллекция моделей. Игрок открывает готовую модель, рассматривает её и читает справку о прототипе, красит, меняет детали, ставит свет и механизмы, проверяет и подстраивает, собирает здание «из литников» или строит своё. Результат попадает в каталог Build и на макет.

Три слоя режима:

| Слой | Что даёт игроку | Подраздел |
|---|---|---|
| Collection | витрина, осмотр, справка по реальному прототипу, открытие моделей | §22.7.1 |
| Workshop | покраска, детали, свет и механизмы, стенд (тест и подстройка), реставрация | §22.7.2 – §22.7.4 |
| Builder | сборка из литников и генерация зданий | §22.7.5, §22.7.6 |

**Icon Studio и Track Studio остаются инструментами автора контента** ([ATTN_20](docs/ATTN_20_track_studio.md) §20.1: «не часть игры и не для игрока»). Они не превращаются в экраны игрока. Library берёт у них код: мир с объектом, камеру, Fit, слоты ракурсов, окно и файл настроек, сборщик материалов, схему «список, рабочая копия, проверка, запись».

**Название [решено].** «Library» это название режима и кнопки на `ModePanel` (то, что видит игрок). «Model Studio» это название рабочего экрана мастерской внутри режима. Код остаётся в `core/library/`, идентификатор режима `&'library'` не меняется (он зашит в `Global.current_mode`, `ModeController`, `Hints`). Закрывает три открытых вопроса о названии (ATTN_17 §17.12.12 п. 3, ATTN_18 §18.7 п. 7, ATTN_19 §19.11 п. 5); вопросы закрыты в этих документах (§22.13). 

**В объёме:** всё перечисленное в таблице слоёв; правила режимов игры и сложности (§22.4); рабочий экран и выход из него (§22.5); данные игрока (коллекция, исполнения); план интерфейса; шаги L0–L12 с проверками в редакторе.

**Вне объёма:** содержание кампании (главы, цели, награды: [ATTN_19](ATTN_19_game_flow.md) §19.10); система повреждений в игре (GDD §10 «Мастерская повреждений»: Library получает только заготовку, §22.7.4); звук (TDD roadmap п. 6, у Library только слот); импорт чужих моделей игроком; онлайн и обмен блюпринтами (формат данных готов к нему, §22.6.2).

## 22.3. Принципы

1. **Один объект, один путь [предложение].** Любое действие Library применяется к `EntitySetting` и данным исполнения (`ModelVariant`). Нового типа сущности «модель коллекции» нет.
2. **Данные, не ветвление кода [предложение].** Исполнение, паспорт, набор это данные; код читает их, а не знает про конкретные модели.
3. **Ядро без интерфейса [решено в ATTN_20 §20.2, переносится].** Всё, что можно вызвать без окна (применение исполнения, раскладка литника, сборка здания, проверки), лежит без `Control` и тестируется сценами `tests/library_*`.
4. **Тот же код, что в игре [решено в ATTN_18 §18.2, переносится].** Объект в студийной сцене создаёт `EntityFactory`; свет и фон студийные, `GFX` игры не используется.
5. **Без наказания [решено, GDD §2].** Нет таймеров, штрафов и необратимых действий; любой шаг можно отменить или сбросить.
6. **Каждая опция имеет флаг [предложение].** Интерфейс спрашивает `LibraryRules`, а не режим игры (§22.4).
7. **Контент автора в `res://`, данные игрока в `user://` [предложение].** Запись в `res://` работает только из редактора ([ATTN_20](docs/ATTN_20_track_studio.md) §20.1); игрок пишет в `user://` и только JSON (F7).
8. **Старое не ломается [предложение].** Сейв без поля исполнения, модель без паспорта и без разметки деталей работают как раньше.

## 22.4. Режимы игры, сложность и отключение опций

**[=атн=] «Учесть отключение определённых опций для режимов игры песочница\прохождение кампании\уровень сложности».** Устройство то же, что у электрики ([ATTN_10](docs/ATTN_10_dc_power_system.md) §10.5.11): сложность это выбор пресета плюс отдельные тумблеры. Пресеты Library соответствуют точности электрики: Простая это P0, Стандарт P1, Реалистичная P2.

**`LibraryRules`** (ресурс, код без интерфейса) **[предложение]**. Интерфейс не знает про «песочницу» и «кампанию», он спрашивает ключ: `rules.level(&"paint")`, `rules.allows(&"parts.swap")`.

| Ключ | Тип | Значения |
|---|---|---|
| `source` | enum | `SANDBOX`, `CAMPAIGN` |
| `preset` | enum | `SIMPLE`, `STANDARD`, `REALISTIC` |
| `catalog.open` | bool | все модели открыты |
| `paint.level` | 0–3 | 0 нет; 1 цвет зон; 2 плюс отделка; 3 плюс декали и износ |
| `parts.swap` | bool | замена деталей |
| `fit.level` | 0–2 | 0 готовое; 1 включить и выключить; 2 установка и проводка |
| `test.level` | 0–2 | 0 кнопка «Проверить»; 1 стенд с показаниями; 2 ручная подстройка |
| `kit.mode` | 0–2 | 0 пропуск; 1 упрощённая; 2 полная |
| `gen.level` | 0–2 | 0 готовые здания; 1 модули; 2 плюс правила прототипа |
| `restore.enabled` | bool | реставрация |
| `debug.all` | bool | открыть всё (только debug) |

Стартовые значения **[предложение]**:

| Опция | Песочница, Простая | Песочница, Стандарт | Песочница, Реалистичная | Кампания |
|---|---|---|---|---|
| Коллекция | открыта | открыта | открыта | открывается опытом и главами |
| Справка о прототипе | да | да | да | да |
| Покраска | 1 | 2 | 3 | по главе |
| Замена деталей | нет | да | да | по главе |
| Свет и механизмы | готовые (0) | включать (1) | установка (2, нужна ATTN_16 C1 и ATTN_10 D7) | по главе |
| Тест | кнопка (0) | стенд (1) | подстройка (2) | по главе |
| Сборка | пропуск (0) | упрощённая (1) | полная (2) | по главе, как награда-ритуал |
| Генератор | готовые (0) | модули (1) | плюс прототип (2) | по главе |
| Реставрация | нет | по желанию | по желанию | задания |

**Где хранятся.** Правила лежат в сейве макета (как `ControlMode`, ATTN_16 D10, и `DCSRules`, ATTN_10) и в профиле как значение по умолчанию для Library, открытой без макета. Выбираются в `sandbox_setup` ([ATTN_19](ATTN_19_game_flow.md)); до него пресет переключается в отладочной кнопке шапки Library. Кампания переопределяет правила главы (`Chapter`, ATTN_19 §19.10). Когда появятся `DCSRules` и `ControlMode`, `LibraryRules` становится секцией общих правил игры (Q7).

**Как выглядит отключённая опция [открыто, Q8].** Предложение: серая с причиной («Доступно в режиме Стандарт»), кроме Простой, где такие опции скрываются, чтобы не загромождать экран.

**Открытие моделей.** Источники: опыт (XP) за действия в Library и награды глав. Денег нет. XP лежит в профиле. Проигрыша нет: закрытая модель остаётся серым силуэтом с условием открытия.

## 22.5. Рабочий (переходный) экран

### 22.5.1. Предложение: один экран, сменные рабочие области

Экран `library` (в ATTN_19 числится как `studio`, Q2) это одно окно с одним 3D-миром (`StudioWorld` в `SubViewport`) и сменными рабочими областями (`Workspace`): Осмотр, Покраска, Детали, Свет, Стенд, Реставрация, Сборка, Здания. Выбранный объект, камера и исполнение общие, поэтому переходы мгновенны, а «применить исполнение» написано один раз.

```
game (кнопка Library на ModePanel)
  └─→ library  (оверлей поверх игры, мир игры на паузе)
        ├─ Осмотр ........... тот же экран, сцена Clean / Витрина
        ├─ Покраска, Детали, Свет, Стенд, Реставрация ... тот же экран, сцена Clean / Стол
        ├─ Сборка ........... тот же экран, своя рабочая область (стол с литниками)
        ├─ Здания ........... тот же экран, своя рабочая область (плита-основание)
        └─ Студии автора .... кнопки верхней полосы Library: Track Studio, Icon Studio, Room Studio;
                              разворачиваются в дочернем окне на месте Model Studio (§22.5.4)
  ←─ «Назад» / Esc: возврат в игру, в прежний режим HUD
```

**Правило выбора «отдельная сцена или один экран» [решено]:**

| Тип | Решение | Причина |
|---|---|---|
| Всё для игрока (осмотр, мастерская, сборка, здания) | один экран | общий мир, камера, выбранный объект; нет загрузок между шагами |
| Инструменты автора (Track Studio, Icon Studio, Room Studio) | кнопки верхней полосы Library, дочернее окно | общий оверлей и общая «Назад»; пишут в `res://`, поэтому кнопки прячутся флагом `SHOW_AUTHOR_STUDIOS` (§22.5.4, шаги L1b, L1c) |
| Будущие тяжёлые редакторы (например профили рельса игрока) | отдельная сцена по необходимости | собственная геометрия и ввод |

### 22.5.2. Вход и выход

- **Первая версия (L1) [решено]:** вход без роутера. `ModeController` запоминает предыдущий режим, открывает `LibraryScreen` оверлеем (`CanvasLayer`), ставит дерево на паузу (экран `process_mode = ALWAYS`), выключает 3D главного вьюпорта на время (`Viewport.disable_3d`, проверить в редакторе). При закрытии возвращает прежний режим и подсвечивает его кнопку.
- **После ATTN_19 F1:** вход через `SceneRouter.push('library')`. Экран делается по контракту `Screen` (`enter`, `exit`, `can_leave`), поэтому смена способа входа не меняет код экрана. Пауза Observe и правила паузы: [ATTN_19](ATTN_19_game_flow.md) §19.8.
- **Из главного меню (`menu`)**: `Model Studio` открывает тот же экран без макета (правила из профиля).
- Запуск отдельно для разработки: F6 на `library_screen.tscn` (окно по настройкам проекта, размер и положение окна Library не запоминает).

### 22.5.3. Вид сцены: варианты

| Вариант | Что это | Плюсы | Минусы, стоимость |
|---|---|---|---|
| A. Чистая студия | нейтральный фон и студийный свет, как Icon Studio | уже есть код; лучшая читаемость модели; быстрый; годится для скриншотов и отладки | без «ощущения мастерской» |
| B. Стол моделиста | коврик, лампа, инструменты-декор, модель на столе | задаёт настроение Workshop; лампа даёт настоящий свет | немного декора из коробок и существующих материалов |
| C. Витрина со стеклянными полками | 3D-стеллаж, модели стоят по полкам | коллекционный азарт, «полка успехов» | стекло: дорогие отражения; взять упрощённый материал (прозрачность и Fresnel, без SSR); расстановка по коллекции |
| D. Витрина от первого лица | свободный обход стеллажа WASD и мышью | иммерсивность | нужны границы, высота камеры, коллизии; смысл есть только вместе с C |
| E. «Уголок моделиста» (нечто другое) | стеллаж над столом: модель с полки плавно «переезжает» на стол, камера сопровождает | единая композиция, B и C в одной сцене | стоит как B плюс C |

**Решено:** общая оболочка с заменяемой сценой (`LibraryStage`: `clean`, `bench`, `shelf`). Идти по порядку: A (L1–L11), затем E как итоговый вид (L12), D только как необязательная опция E. Чистая студия остаётся навсегда как переключатель (скриншоты, слабые машины). Комнату Observe (`RoomBuilder`) не использовать: она привязана к `ObserveController`, а `fast_debug` сейчас её отключает (F9); фон Library строится из коробок. Look `workshop` ([ATTN_14](ATTN_14_observe_room.md)) подходит как стартовый для E.

### 22.5.4. Студии внутри Library [решено]

Верхняя полоса `LibraryScreen` (оболочка): «Назад», название, кнопки `Model Studio`, `Track Studio`, `Icon Studio`, `Room Studio`. Всё ниже полосы это дочернее окно выбранной студии на всю ширину и высоту. `Model Studio` это прежний экран Library целиком: вкладки областей (Осмотр … Реставрация), плашка правил, каталог, окно модели, панель данных, нижняя подсказка. Track Studio, Icon Studio и Room Studio разворачиваются в дочернем окне вместо него.

| Вопрос | Решение |
|---|---|
| Окно | Студии окном не управляют: размер, положение и заголовок окна не меняются. Работа с окном убрана из `StudioSettings`, Track Studio и Icon Studio; кнопка «Сбросить окно» стала «Сбросить панели» |
| Отдельное приложение | не нужно: `StudiosApp` и запуск F6 убраны. Рассматривались отдельное приложение, второй процесс Godot и `Window` внутри игры; выбрано встраивание: один оверлей, общая пауза, общий выход |
| Жизнь студий | Model Studio создаётся при открытии Library и живёт до её закрытия; при переключении скрывается (`visible = false`, `process_mode = DISABLED`: клавиши и таймеры спят, `SubViewport` не рисуется). Track, Icon и Room создаются при открытии и освобождаются при уходе (как делал `StudiosApp`): `_exit_tree` записывает их настройки |
| Несохранённое | «Назад», кнопки студий (уход из Track, Icon, Room) и закрытие Library сперва спрашивают активную студию методом `request_leave(proceed)`. Track Studio показывает свой диалог «Отбросить?» и продолжает после подтверждения; Icon Studio и Room Studio несохранённого не держат; Model Studio передаёт вопрос рабочей области (`can_leave`). Из Model Studio в другую студию переключение вопроса не задаёт: Model Studio остаётся в памяти |
| Клавиши | У Model Studio F, 1–6 и клавиши области; у Track Studio и Icon Studio свои (F, P, 1–9); скрытая студия клавиш не получает. Esc закрывает Library только из Model Studio: в остальных студиях выход кнопкой «Назад» (Esc в поле ввода не должен закрывать экран) |
| Скрытие кнопок | `LibraryScreen.SHOW_AUTHOR_STUDIOS`: `false` прячет полосу студий, остаётся один Model Studio. До релиза значение `true`, на релизе `false`: студии пишут в `res://` |

### 22.5.5. Комнаты и Room Studio [решено автором, подробности: ATTN_25]

Архитектура комнат, правила смены, пайплайн Blender и план RM0–RM9 живут в [ATTN_25_rooms.md](ATTN_25_rooms.md); здесь только то, что касается Library.

- **Принцип.** Игрок занимается макетом в комнате и комнату не правит. Активную комнату выбирает на старте игрок или сценарий, в ходе сессии её меняет только админ (`Global.debug_mode`) или сценарий. Observe комнату не настраивает: только свет и механизмы комнаты, сделанные для него.
- **Room Studio** это инструмент автора и админа для карточек комнат `RoomConfig` (`data/rooms/cards/<id>.tres`, как карточки вагонов и траков лежат отдельно от моделей) и их сцен. Комната не `Entity`: у неё свой конфиг и сцена. Процедурная комната сцены не имеет и в просмотре недоступна (временно, пока их заменяют сцены из Blender). Графика (Look, Time, Quality) остаётся там, где есть: F3 → Graphics.
- **Запуск.** Кнопка «Room Studio» в Library и F6 на `room_studio.tscn` (RM4; сейчас студия создаётся из скрипта и по F6 не запускается).
- **Оставить активной.** Комнату, выбранную в Room Studio, можно оставить активной при выходе из Library: переключатель «Оставить активной при выходе», сигнал `room_keep_requested(id)` по образцу `place_requested` (RM4). Виден только админу.
- **Сейчас (L1c): просмотрщик.** Список комнат из `RoomCatalog` (процедурные серые), окно просмотра сцены комнаты, паспорт справа только для чтения. Окно просмотра: отдельный `World3D`, нейтральный свет, свободная камера, переключатель потолка. Свет и небо игры не показываются: их проверяют в Observe.
- **Дальше.** Вкладки «Паспорт», «Объекты» (управление светом и механизмами комнаты, в том числе нодами, созданными в сцене Godot), «Проверка»; кнопка «Обновить из сцены» (числа карточки из меток `.glb`): RM5 и RM8 в ATTN_25.

### 22.6.3. Связь с игрой

- **`VariantApplier.apply(instance, variant, info)`** применяет исполнение к экземпляру сцены: покраска (`surface_override_material` на **копии** базового материала, общий ресурс не меняется), детали (по ролям `PartRegistry`), свет (`LightConfig` копией), подстройка (копия `WagonConfig`). Работает одинаково в Library и в игре.
- **`C_Visual`** получает поле `variant` (Dictionary), применяет в `_on_instance_ready`, пишет в `save_data`. Старый сейв без поля грузится как раньше.
- **`EntityFactory.create_from_setting(setting, style_id := &"", variant := {})`**: второй параметр `style_id` уже занят стилем трака (ATTN_17 §17.13, U3c), исполнение идёт третьим необязательным параметром, по умолчанию пусто (прежнее поведение). Запрос стиля (`style_request`) и исполнение независимы.
- **Каталог Build:** категория «Мои исполнения» и «Мои здания» через провайдер каталога ([ATTN_17](ATTN_17_ui.md): `LibraryProvider`, шаблон `CatalogProvider`). Для Library коллекция берётся из `Global.object_dirs`.
- **Макет переносим:** исполнение и спецификация здания записываются в сейв макета **целиком**, а не ссылкой на файл `user://`; удаление файла исполнения макет не ломает.
- **Контур и подсветка** (`material_overlay`, `next_pass`) независимы от `surface_override_material`; проверка на совместимость в L4.

## 22.7. Модули: анализ и предложения

### 22.7.1. Collection: витрина, осмотр, справка

**Что:** каталог с поиском и фильтрами по фасетам (`CatalogMeta.FACET_SPECS`), паспорт модели, осмотр (орбита, Fit, шесть слотов ракурсов, автовращение), габариты из замера AABB в ю и в «метрах прототипа» (1 ю около 1 м, [ATTN_20](docs/ATTN_20_track_studio.md) §20.2), состояние «закрыто или открыто».

**Справка по реальному прототипу:** данные из `ModelInfo.prototype` (дорога, серия, производитель, годы, роль) и короткая история. Контент пишет автор; пока паспорта нет, показываются имя, габариты и теги.

**Вид:** варианты A–E §22.5.3.

### 22.7.2. Customization: покраска, замена деталей, исполнения

Обширный раздел, делится на ступени (включаются правилами §22.4):

| Ступень | Что | Как | Ограничение |
|---|---|---|---|
| Цвет зон | покраска по зонам | зоны это поверхности меша (surface) или роли `PartRegistry`; `surface_override_material` на копии материала | у моделей с одной поверхностью только «весь корпус» (F3) |
| Отделка | матовая, глянец, металл | параметры `StandardMaterial3D`: шероховатость, металличность | шейдер колёс `shader_wheel01_material` это отладочный элемент: `C_TrainVisual` вешает его как `material_overlay` на `WheelPairMesh`. Вводится флаг (имя и место решаются в L3), по умолчанию выключен; с выключенным флагом колёса красятся как остальное =атн= шейдер - элемент дебага. Включение флагом **[<mark>сделано</mark>]** |
| Декали | номера, надписи, полосы | узел `Decal` движка (Forward+), дочерний узел кузова, следует за вагоном | лимит кластерных элементов делится со светом: проверить в редакторе, бюджет ввести числом |
| Износ | потёртости, грязь | параметры шейдера-накладки (`material_overlay` занят контуром, нужен второй путь) | подтвердить способ в L3 |
| Детали | замена по ролям | опции `PartSlot` заменяют узел по роли | **нужна разметка моделей** (F3); без неё раздел пуст |
| Свет и механизмы | включение, цвет, добавление из пресетов | `LightConfig` и механизмы ([ATTN_16](ATTN_16_mechanisms.md)); уровень по `fit.level` | установка (уровень 2) только после ATTN_16 C1 и ATTN_10 D7; звук это слот-заглушка (TDD roadmap п. 6) |
| Кисть разная | рисование краской по модели | маска по UV модели (текстура маски на зону); накладка-шейдер смешивает цвет и отделку по маске | нужна неперекрывающаяся UV у модели (проверить в Blender); без неё остаются зоны |
| Скотч | защита области от кисти | вторая маска «закрыто»; кисть по закрытому не рисует; снять можно целиком или по линии | тот же UV; управление: полоса по двум точкам на поверхности |
| Стирка | снять краску, грязь, износ | кисть с обратным действием по маске краски и по слоям `dirt`, `wear` | основа реставрации (§22.7.4) |


**Главный риск:** монолитные модели (F3). Решение: покраска и осмотр работают на нынешних моделях, замена деталей включается по мере разметки моделей автором в Blender (`Custom Property` `role`, поддерживается `PartRegistry`).

#### 22.7.2.1. Покраска: архитектура [предложение]

Задача целиком: покраска целиком и частично, аэрограф и кисть, сухая кисть, подчёркивание деталей, стирание сразу и участками с разной толщиной, скотч (группа C2), а дальше износ, грязь и реставрация. Ниже способ сделать это так, чтобы форматы данных и показ не переписывались при добавлении инструментов. Полный список инструментов автор даст позже: новые инструменты должны ложиться в эту схему.

**Главная идея.** Краска это слои. Слой хранит, где и насколько густо нанесена краска (покрытие), а всё остальное (цвет, глянец, способ смешивания) это параметры слоя. Инструменты не отдельные подсистемы, а настройки одного «штампа»: кисть, аэрограф, сухая кисть, ластик отличаются размером, мягкостью краёв, накоплением, шумом и знаком (рисует или стирает). Показ один: шейдер-накладка поверх материала модели складывает слои.

```
мышь ──► попадание луча в модель: точка, нормаль, поверхность (surface)
              │
              ▼
   «штамп»: шар радиуса R вокруг точки в 3D
              │  для каждого пикселя карты краски (UV2) берётся его 3D-позиция
              │  из карты позиций модели и сравнивается с центром штампа
              ▼
   слой краски (RGBA, UV2)  ◄── маска скотча (R8, защищает от штампа)
              │
              ▼
   шейдер-накладка на поверхностях модели: грунт + слои ─► цвет, шероховатость, металл
```

**Почему штамп считается по 3D-позиции, а не по UV.** Круг на экране в UV превращается в искажённое пятно, а швы развёртки рвут мазок. Если сравнивать 3D-позицию каждого пикселя карты краски с центром штампа, размер кисти постоянен по поверхности, швов нет, а мазок не «перетекает» на обратную сторону тонкой детали (проверка нормали).

**Из чего состоит (каждая часть заменяема отдельно)**

| Часть | Что делает | Меняется без переписывания остального |
|---|---|---|
| Схема исполнения v2 (данные) | список слоёв с параметрами; файлы слоёв (PNG) рядом | да: JSON с версией `v`, лишние поля не теряются |
| `PaintEngine` (нанесение) | принимает штамп (центр, радиус, цвет, поток, знак, шум, защита) и меняет слой | да: GPU-версия (штамп по карте позиций) или CPU-версия (запасная); формат слоя один |
| `PaintTarget` (где лежит) | какие `MeshInstance3D` модели красятся, их карты позиций, их слои | да |
| Шейдер-накладка (показ) | грунт и слои в итоговый цвет; подчёркивание рельефа | да: способ крепления к модели (`next_pass` или `material_overlay`) за одним классом |
| Инструменты | пресеты параметров штампа, мышь и планшет (нажим) | новый инструмент = новый пресет; код нужен только для особых (скотч, смывка) |

**Слой (данные)**

```
paint: {
  "layers": [
    { "id": "base", "name": "Грунт", "coverage": "zones",
      "zones": { "all": { "color": "#c0392b", "finish": "gloss", "cover": true },
                 "Body#3": { "color": "#f1c40f", "finish": "keep", "cover": false } },
      "blend": "normal", "opacity": 1.0, "relief": 0.0, "visible": true },
    { "id": "p1", "name": "Камуфляж", "coverage": "texture", "file": "p1.png",
      "blend": "normal", "opacity": 1.0, "finish": {...}, "relief": 0.0, "visible": true }
  ],
  "protect": { "file": "protect.png" }          // скотч, по необходимости
}
```

- `coverage: "zones"`: покрытие задаётся целой поверхностью (surface) или всей моделью. Id зоны: `all` или `<имя меша>#<номер поверхности>`; у зоны `color`, `finish` (`keep`, `matte`, `satin`, `gloss`, `metal`) и `cover` (кроющая краска или лессировка). Не нужна ни UV, ни карта позиций. Это и есть «покраска целиком одним цветом», шаги L3 и L4.
- `coverage: "texture"`: покрытие и цвет лежат в RGBA-картинке в UV2 (альфа это толщина краски). Нужна для кисти, аэрографа, сухой кисти, скотча и ластика, шаги C2.
- `blend`: `normal` (краска), `multiply` (смывка, затемнение), `screen` или `overlay` (подсветка).
- У грунта кроющая способность это `cover`: кроющая краска закрывает рисунок модели, лессировка накладывает цвет на рисунок (сквозь неё видны детали). Плавный `opacity` появляется у слоёв с текстурой (C2). «Весь корпус» не красит прозрачные поверхности (стекло), чтобы окна оставались стеклом.
- `relief` от -1 до 1: слой оседает в углублениях (смывка, отрицательные значения) или на выступах и кромках (сухая кисть, подсветка кромок, положительные). Считается в шейдере по кривизне, без дополнительных данных; позже можно подставить запечённую карту кромок (тот же параметр).
- До 4 слоёв с текстурами, не считая грунта. Слой PNG 1024×1024 это 4 МБ видеопамяти (2048×2048 это 16 МБ); размер задаётся в паспорте модели (`paint_res`).

**Как получить каждую возможность**

| Нужно | Как |
|---|---|
| Покраска целиком | слой «Грунт»: цвет, кроющая способность, отделка (`finish`) |
| Сплошная или частичная | сплошная: грунт или «Залить слой»; частичная: кисть или аэрограф по участку, границы держит скотч |
| Кисть | жёсткий край, малый шаг штампов, поток 1 |
| Пульверизатор (аэрограф) | мягкий край, малый поток; краска копится, пока кнопка удержана на месте; радиус растёт с нажимом (планшет) |
| Сухая кисть | штамп-«щетина» (шум по 3D-позиции); запас краски убывает вдоль мазка, мазок рвётся в конце; слой с `relief` больше нуля, поэтому краска ложится на выступы |
| Подчёркивание деталей | смывка (`multiply`, `relief` меньше нуля: тёмная краска в углублениях) и подсветка кромок (светлее на выступах); кнопки «по всей модели» (заливка слоя без кисти) и кисть для выборочного |
| Стирание сразу | Ctrl+Z, Ctrl+Y; история снимков слоя (сжатые, глубина около 30) |
| Стирание участками и разной толщины | ластик: размер, мягкость, сила (на сколько уменьшает толщину краски, 0–100%); стирает выбранный слой |
| Скотч | маска защиты: линия по экрану между двумя точками проецируется на модель; штамп умножается на (1 − защита); снимается целиком или тем же ластиком |
| Износ, грязь, реставрация (дальше) | те же слои и ластик; реставрация это стирание слоёв и перекраска, второго движка не нужно |
| Декали (дальше) | штамп с рисунком вместо круга в отдельный слой «Декали»; запечённые, повторно не правятся (вариант с узлами `Decal` решить позже) |

**Что требуется от моделей.** Для режима `texture` нужна вторая развёртка UV2 без перекрытий. В Godot её даёт импорт: в окне Advanced Import Settings модели Meshes, Light Baking, Static Lightmaps (VoxelGI/SDFGI/LightmapGI) создаёт UV2; либо вторая развёртка из Blender (импортируется как UV2). В экспортированной игре развёртку сгенерировать нельзя, UV2 должна лежать в импортированной модели. Без UV2 у модели доступна только покраска зонами (грунт). В шаге L3 добавляется скрипт проверки: какие модели имеют UV2 и не перекрывается ли она.

**Как включить UV2 в этом проекте.** Сцены моделей (`data/trains/loco_02_el1.tscn`, `loco_02_el2.tscn`, `wagon_02.tscn`, `data/buildings/default_house.tscn`) содержат собственные (встроенные) меши и не ссылаются на исходный `.glb`, поэтому параметр импорта «Static Lightmaps» у `.glb` на игровые меши не влияет. UV2 создаётся в самой сцене: открыть сцену, выбрать `MeshInstance3D` (`Elect_1_Elect_1_0`, `Elect_2_Elect_2_0`, `F_CentreSill`, `BL001_Eckstaender`), в панели 3D меню Mesh, «Unwrap UV2 for Lightmap/AO», затем Mesh, «View UV2» (должны быть видны острова развёртки без наложений) и Ctrl+S. Развёртка пересобирает поверхности (вершины на швах дублируются), поэтому перед этим стоит зафиксировать состояние в git и после проверить, что материалы поверхностей на месте. Новые модели лучше подключать как сцену-наследник `.glb` с включённым «Static Lightmaps»: тогда UV2 создаётся при импорте. Проверка по всем моделям: `tests/uv2_audit.gd` (File, Run, Ctrl+Shift+X): печатает по каждому видимому мешу число поверхностей, у скольких есть UV2, заполнение атласа, долю перекрытий и вердикт.

**Монолитные модели.** Кисть решает вопрос одной поверхности у `loco_01`: раздельные кабина, рама и корпус получаются не разделением материалов в Blender, а покраской участков по UV2. Разделение материалов нужно только для быстрой заливки зоны одним нажатием.

**Хранение и сейв.** Краска хранится как PNG слоёв (штрихи не записываются): рядом с исполнением, `user://library/variants/<id>/<слой>.png`. В сейв макета исполнение входит целиком: параметры и байты PNG (разреженная краска сжимается до десятков килобайт), поэтому макет остаётся переносимым ([ATTN_22](ATTN_22_library.md) §22.6.3). Формат JSON v2 вводится сразу в L3, чтобы его не менять в C2.

**Как стыкуется с игрой.**

- Накладка вешается цепочкой `next_pass` на дубликат материала поверхности (`surface_override_material`), общий материал модели не меняется. Контур выделения (`material_overlay`) остаётся независимым. Если `next_pass` даст мерцание на совпадающей геометрии, способ крепления меняется в одном классе (`PaintTarget`).
- Колёса: отладочный шейдер колёс включается флагом и стоит в `material_overlay`, на покраску не влияет.
- Тележки и колёсные пары строятся из других сцен (`C_TrainVisual._build_bogies`); красится кузов (меши сцены модели).

**Риски и что проверяется прототипом до основной работы (шаг C2.0).** Godot не запускался, поэтому следующие вещи нужно подтвердить на маленькой сцене до того, как на них опирается C2:

1. Накопление в `SubViewport` (`render_target_clear_mode = NEVER`, обновление `UPDATE_ONCE` по штампам): должна рисоваться краска без стирания предыдущих мазков.
2. Карта позиций: в прототипе строится на CPU во float32 (растеризация треугольников в UV2), поэтому вопрос точности половинной точности RGBA16F снят; проверяется время построения (кэшируется на диск) и покрытие.
3. `next_pass` с альфа-накладкой: нет мерцания (z-fighting) и нет конфликта с контуром выделения.
4. UV2 у `loco_01`, `wagon_02`, `house_01`: есть ли и не перекрывается ли (скрипт проверки).
5. Скорость: 1024×1024, штамп за кадр без просадки fps; снимок для отмены не вызывает паузу.

Если п. 1–2 не подтвердятся, включается CPU-версия `PaintEngine` (луч по треугольной сетке, барицентрическая UV, штамп в `Image`): слабее на швах, но формат слоя, шейдер и данные те же, переписывать нечего.

**Автопроверки** (запускаются сами после загрузки, повтор клавишей `S`, отчёт клавишей `P`; итог в Output «C2.0: проверок n/m»):

2. Накопление: красный штамп с одной стороны, затем синий с другой; красная краска не должна пропасть.
3. Набор краски: два штампа с потоком 0.5 в одну точку; максимум альфы должен вырасти.
4. Стоимость прохода штампов (32 штампа за кадр, GPU и CPU, мс) и чтения слоя для отмены (мс, размер после сжатия FastLZ).
5. Информация о том, какой цвет реально лежит в слое после снятия премультипликации.

**Что прислать после запуска:** строки Output целиком (для сферы и для хотя бы одной вашей модели) и ответы на вопросы, которые автопроверки не видят:

**Принятые решения (по результатам).** Движок штампов на GPU (`SubViewport` с накоплением) подходит, CPU-запасной вариант не нужен. Накладка крепится цепочкой `next_pass` на override-копии поверхностей (`material_overlay` остаётся за контуром и подсветкой состояний), сдвиг по нормали не используется. Карта позиций строится на CPU в рабочем потоке (2.7 с на 1024, не блокирует) и кэшируется на диск в C2.1b. Снимок для отмены делается при завершении штриха.

**Как читать результат.** Если накопление и набор краски PASS, GPU-движок штампов подходит, дальше C2.1 строится на нём. Если FAIL, включается CPU-версия `PaintEngine` (луч по треугольной сетке, штамп в `Image`): формат слоя, шейдер накладки и данные остаются теми же. Режим накладки (`next_pass` или `material_overlay`) и разбор цвета (`G`, `M`) фиксируются по вашим ответам и записываются в этот раздел.

### 22.7.4. Реставрация

**Статус: вероятно** (решение автора): в плане L11 остаётся, в roadmap TDD помечена «вероятно».

**Что:** игрок возвращает потрёпанную модель в хорошее состояние; это элемент заданий кампании и позднее связь с системой повреждений (GDD §10).

**Заготовка без системы повреждений:** износ, грязь и ржавчина это поля исполнения (`wear`, `dirt`, `rust`). Задание `RestorationTask`: исходное «ухудшенное» исполнение, цели (износ не выше порога, заменить детали, перекрасить) и инструменты: чистка (грязь), зачистка (ржавчина), покраска (L3), замена деталей (L5). Индикатор прогресса как у чистки в аналогах.

**Что нужно решить до L11:** нужен ли в игре компонент повреждений (`C_Damage`) и как вагон после схода попадает в Library (GDD §10). Это не входит в L11; L11 делает инструменты и задания на исполнениях. Не путать с Challenge «диагностика макета» (F14).

### 22.7.5. Сборка «из литников»: анализ идеи

**Статус: вероятно** (решение автора): весь раздел и шаги L9–L10 в roadmap «вероятно». **Авторские литники допустимы, если идея взлетит:** прототип `house_01` уже есть в Blender, разобран по литникам. Тогда первый путь L9 это части и литники из Blender (с ролями `PartRegistry`), а авто-литник из частей генератора остаётся запасным.


**Идея:** здание приходит набором на литниках; игрок срезает детали, ставит их на основание и красит. Ритуал сборки из реального хобби; связь с открытием моделей и с «от готового к собранному» (GDD §2).

**Плюсы:** эмоциональный якорь режима («ритуал сборки», GDD §7); награда за кампанию; видимый результат; хорошо ложится на Tiny-Glade-подобную генерацию.

**Риски:** стоимость контента (каждая модель требует разделённых деталей и разметки шагов); утомительность (по отзывам о Model Builder); выбор мелких деталей мышью; монолитные модели (F3).

**Предложение [предложение]:**

- **Литники строятся автоматически из частей генератора зданий** (L7): стеновая панель, угловая стойка, скат крыши, окно, дверь, труба. Авторских литников нет: `SprueLayout` раскладывает части по рамкам, добавляет перемычки (runners) и литники (gates). Контент стоит столько же, сколько генератор. Поэтому генератор идёт раньше сборки (L7–L8, затем L9–L10).
- **Для вагонов и локомотивов литников нет**, пока модели монолитны (Q10). Возможная замена: «доводка» (зачистка швов, покраска, декали) без разборки.
- **Взаимодействие:** клик по части «срезает» её (анимация, след литника остаётся); перетаскивание на призрак с магнитом к сокету; неверная часть мягко возвращается; зачистка и клей необязательны. Без физики мелких деталей (движение твином).
- **Без наказания:** нет таймеров и ошибок; кнопки «Отменить шаг» и «Собрать само».
- **Режимы (`kit.mode`):** 0 пропуск (здание готово сразу), 1 срезать и поставить, 2 полный порядок с зачисткой и клеем.
- **Качество:** только косметика (видимость швов), без влияния на геймплей [открыто].

### 22.7.6. Генерация зданий (паттерн Tiny Glade): анализ идеи

**Идея:** здание строится из простых действий: контур на плите, высота этажей, крыша; окна и дверь расставляются правилами; «Другой вариант» меняет сид.

**Что берём из Tiny Glade:** бессеточный контур, правку тягой за грань, крышу как следствие контура, окна и двери как «контекстные» элементы по размеру стены, детерминированное оживление после структуры, отсутствие проигрыша.

**Что не берём в первой версии:** свободные кривые стены, рост плюща, повреждения штукатурки, взаимодействие соседних зданий.

**Предложение [предложение]:**

- `BuildingSpec` (данные): контур, число этажей, высота этажа, крыша (двускатная, плоская), стиль, сид, переопределения.
- **Контуры v1:** прямоугольник и L-образный из двух прямоугольников (крыша из прямоугольников без skeleton-алгоритма); произвольные многоугольники позже.
- **Правила окон и дверей:** по длине стены, высоте этажа, сиду; дверь на первом этаже у выбранной стены.
- **Геометрия** собирается кодом (`SurfaceTool`) в один `ArrayMesh` с поверхностями по материалам (до пяти), как `TrackMeshBuilder` собирает трак; материалы из PBR-наборов (сборщик `TrackMaterialBuilder`). Блендерных деталей не требуется.
- **Окна дают `GlowRect`** для ночного света ([ATTN_16](ATTN_16_mechanisms.md): сейчас у `house_01` они расставлены вручную): сгенерированное здание светится так же. Контракт `C_Mechanisms` принимает ли `LightConfig` из кода, проверить в L7.
- **Основание:** «юбка» вниз под фундамент; здания встают на землю, трак, поезд и слой гипса (`plaster`, [ATTN_13](ATTN_13_TerrainTools.md) §13.5), как нынешние.
- **Устройство в игре по канону EC** ([ATTN_TDD.md](ATTN_TDD.md) §2): компонент `C_BuildingGen` хранит `BuildingSpec` и строит меш; его сеттинг `buildinggen_setting.gd` по образцу `stylevisual_setting.gd`; данные идут в `save_data`.
- **Бюджет:** число вершин и треугольников эталонных зданий печатается тестом (как `track_style_bench`), порог задаётся по первому замеру.

| R3 | Декали (`Decal`) и стекло делят лимит кластерных элементов со светом | просадка fps, пропажа света | бюджет декалей числом, замер в L12 и L3, упрощённое стекло |
| R4 | `surface_override_material` и служебные слои (`material_overlay`, `next_pass`) | контур или подсветка не видны | проверка в L4; износ идёт вторым путём (L3) |
| R5 | Версионирование JSON | старая игра стирает данные новой | поле `v`, неизвестные поля сохраняются |
| R6 | Стоимость контента (паспорта, разметка, стили зданий) | режим пустой | паспорта необязательны; генератор вместо авторских зданий |
| R7 | Режим большой | долго нет результата | группы A–D дают рабочую мастерскую без генератора и литников |
| R8 | `fast_debug` зашит (F9) | Observe и комната выключены, документы расходятся | Library не зависит от них; автору решить про чтение `--fast` |
| R9 | Два мира рендерятся одновременно при оверлее | просадка fps | `disable_3d` главного вьюпорта на время; замер в L1 |
| R10 | Запись в `res://` работает только из редактора | сборка игрока не сохранит | все данные игрока в `user://` |
| R11 | Старые сейвы без поля исполнения | поломка загрузки | поле необязательное; проверка в каждой группе |
| R12 | Дубль списка папок каталога (F11) | коллекция и lint расходятся | один вызов `EntityCatalogProvider.list_resources` |
| R13 | Объект Library создаётся как настоящий `Entity`: его компоненты ложатся в глобальные группы (`track_socket`, `power_track`, `TGM`) и могут вызвать `PGM.request_recalculate()`. Физика у Library своя (отдельный `World3D`) | остатки в группах или лишний пересчёт сети макета | `kill_me` при закрытии и смене объекта; проверка в L1 п. 5; если проявится, показывать треки сценой (`SOURCE_SCENE`) |

## 22.11. Решения и открытые вопросы

| № | Тема | Статус и предложение |
|---|---|---|
| Q1 | Название | **[решено]** «Library» режим, «Model Studio» экран; папка и идентификатор режима не меняются |
| Q2 | Идентификатор экрана и вход | **[решено]** первая версия оверлеем с паузой, затем `SceneRouter.push`; [предложение] идентификатор экрана `library` (в ATTN_19 `studio`, правка ATTN_19 §19.2 ждёт) |
| Q3 | Где живёт коллекция | [предложение] профиль игрока; макет хранит исполнение внутри себя |
| Q4 | Формат данных игрока | [предложение] JSON в `user://`; `.tres` только в `res://` (F7) |
| Q5 | Один экран или студии | **[решено]** один экран Library; студии автора (Track Studio, Icon Studio, Room Studio) кнопками верхней полосы, в дочернем окне вместо Model Studio (§22.5.4) |
| Q6 | Вид сцены | **[решено]** сначала чистая студия, итог «уголок моделиста» (L12) |
| Q7 | Правила | [предложение] `LibraryRules` своя, вливается в общие правила после ATTN_10 D7 |
| Q8 | Отключённые опции | [открыто] серые с причиной или скрывать в Простой |
| Q9 | Открытие моделей | [предложение] опыт и награды глав, без денег |
| Q10 | Вагоны и литники | **[решено]** раздел «вероятно» (решение автора); авторские литники возможны (`house_01` в Blender разобран по литникам); для вагонов литников нет, «доводка» позже |
| Q11 | Контуры генератора | [предложение] прямоугольник и L-образный в первой версии |
| Q12 | Награды кампании | [открыто] структура `Chapter.unlocks` в ATTN_19 §19.10 |
| Q13 | Стенд и `PGM` | [открыто] виртуальное питание или локальная сеть; согласовать с ATTN_10 §10.10 |
| Q14 | Повреждения | [открыто, реставрация «вероятно»] нужен ли `C_Damage` и откуда модель попадает в реставрацию (GDD §10) |
| Q15 | Качество сборки | [открыто] косметика (видимость швов) или без оценки |
| Q16 | Покраска: основа | [предложение] краска это слои с покрытием; инструменты это пресеты штампа; показ шейдером-накладкой (§22.7.2.1) |
| Q17 | Требовать UV2 для кисти | **[решено]** кисть только на моделях с UV2 без перекрытий (в сцене: Unwrap UV2 или наследник `.glb` с «Static Lightmaps»); без UV2 только грунт по зонам. Вторая развёртка из Blender только если действительно понадобится. Включить UV2 у `loco_02_el1`, `loco_02_el2`, `wagon_02`, `house_01` и проверить `tests/uv2_audit.gd` |
| Q18 | Грунт: поведение по умолчанию | [предложение, реализовано в L3] кроющий (`cover`), галочка «Кроющая» переключает на лессировку; стёкла «Весь корпус» не трогает; окна и фары, закрашенные явной зоной, возвращаются сбросом зоны (позже ластиком и скотчем); метка «не красить» от автора позже |
| Q19 | Хранение краски | **[решено, реализовано в C2.1b]** PNG слоёв как источник истины; в файле исполнения PNG рядом, в сейве макета и у сущности байты PNG внутри исполнения; штрихи не пишутся |
| Q20 | Слои и уровни правил | [предложение] до 4 слоёв с текстурой, не считая грунта; `paint.level`: 1 грунт, 2 плюс кисть, аэрограф, ластик, 3 плюс сухая кисть, смывка, кромки, скотч |
